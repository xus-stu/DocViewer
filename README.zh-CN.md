# DocViewer — RTF / TXT / Markdown 多文件阅读器

一个 **零依赖、纯前端** 的多文件阅读器：深色为主的界面，
支持同时打开多个 `.rtf` / `.txt` / `.md` 文件并在侧栏切换、**文件拼接**、
**可换字体/主题/文字颜色**、**沉浸式阅读**，内置 **F3 调试面板**。

不需要 Node、不需要 Python、不需要联网。

```bash
open index.html            # 直接双击也可以
./run.sh                   # 用默认浏览器打开
./packaging/mac/build_native.sh   # 打包成 macOS 应用（WKWebView 原生窗口）
```

## 功能一览

### 多文件浏览
- 「打开文件」支持多选；「导入文件夹」递归读取整个目录
- 直接把文件或**整个文件夹**拖进窗口即可导入（自动过滤支持的扩展名）
- 侧栏文件列表：类型图标、大小、类型标签、悬停出现 ×、支持文件名筛选；**超长文件名自动换行**（不截断）
- 侧栏可**单独收起**（侧栏顶部 `‹` 按钮 / `Ctrl+B` / 设置面板），收起时宽度动画缩进去，左边缘出现展开把手，状态会记住
- 侧栏底部：自动换行开关 + 清空；**打开文件 / 导入文件夹** 位于底部（顶部留给文件列表）
- 「记住会话」已移入设置面板，**默认启用**
- `N` 键 / `Alt+↑↓` 在文件之间快速切换
- 会话记忆：刷新或下次打开时自动恢复上次的文件与正文（`localStorage`）

### 文件拼接（只读，不改原文件）
把几个文件按顺序合成一个"阅读视图"，用来对照、串读或拼出完整文档：

1. 在侧栏勾选（或 `Ctrl/⌘` 点选、`Shift` 连选）2 个以上文件 —— 需要调整顺序就直接**上下拖动**行
2. 点选择条上的「**拼接到一起**」，或按 `Ctrl+M`
3. 生成一个新的「拼接文档」条目，原文件条目从列表里收起（**磁盘上的文件一个都没动**）

拼接视图里可以：
- **分段标题**：每段前面显示 `序号/总数 · 文件名 · 类型 · 大小 · 行数`，可一键「标题：开/关」切换成连续排版
- **段间跳转**：`‹` `›` 或 `Alt+←` / `Alt+→`
- **复制 / 导出**：拿到的是带来源标记的完整合并文本 / 单文件 HTML
- **拆开**：一键还原成原来那些文件条目（对象与顺序原样恢复）
- 支持**嵌套拼接**（把已拼好的文档再和别的文件拼）、也支持 MD + TXT + RTF 混合拼接

### 三种格式的呈现

| 格式 | 处理方式 |
|------|----------|
| `.md` | 自带 Markdown 渲染器：标题、列表/任务列表、表格、引用、代码块（含语言高亮）、链接、图片、分割线、目录 |
| `.rtf` | 自带 RTF 解析器：字体表/颜色表、粗体/斜体/下划线/删除线、上下标、字号、前景/背景色、段落对齐缩进、`\par \line \tab`、列表、简单表格、`\'hh` 与 `\uN` 转义 |
| `.txt` | 等宽字体纯文本视图（`.log/.json/.csv/.py/...` 等也按文本处理） |

- **编码自动检测**：BOM（UTF-8/16）→ 严格 UTF-8 → GB18030/GBK → Big5 → Windows-1252 逐级回退，
  中文 GBK 文本与 RTF 中的 `\'d5\'fd`（GBK 十六进制转义）都能正确还原
- **源码 / 渲染切换**：`Ctrl+E` 或工具栏「源码」，任何格式都能看原始文本
- **文档内搜索**：`Ctrl+F`，实时高亮 + 命中计数 + 上下页跳转
- **常用操作**：复制全文、导出为独立 HTML、字号增减、自动换行开关、明暗主题（`data-theme`）

### 动效（可用设置完全关闭）
| 特效 | 说明 |
|------|------|
| 侧栏滑动高亮 | 选中项不是各自变色，而是一块会**滑动**的高亮条；文件图标在选中框内**垂直居中** |
| 文档滑入 | 切换文件时整篇从右侧滑入 |
| 滚动浮现 | 滚动到视口的内容块依次淡入上浮（`IntersectionObserver`，最多 400 块） |
| 平滑缓动滚动 | 搜索跳转 / 分段跳转 / 锚点 / 切换文件都用 `easeOutCubic` 缓动，由帧调度器驱动 —— **帧率越高越细腻** |
| 标签滑动下划线 | 调试面板与设置面板的标签下划线滑动切换 |
| 列表项入场 | 完整强度下依次浮现 |
| 卡片/按钮微交互 | 悬停微抬、按下回弹、图标缩放、选中图标弹跳 |
| 阅读进度条 | 滚动时顶部细线增长，停止后淡出 |
| 面板开合 | 侧栏 / 设置 / 调试面板都是**宽度方向缩进去**（内容同时淡出位移），不是突然消失 |

**时长取标准 UI 动效区间**（`--dur-fast .15s` / `--dur-base .26s` / `--dur-slow .4s`），
设置里两处可控：

- **动画强度**：关闭 / 轻量 / 完整 —— 选「关闭」会移除所有过渡与动画（含 JS 驱动的滚动缓动）
- **动画速度**：快 (×0.7) / 标准 (×1) / 慢 (×1.4) —— 统一缩放所有时长

系统开启「减少动态效果」时，首次运行默认就是关闭状态。

> 调试面板「性能」页顶部有一组**界面动效**读数：滑动高亮的 `transitionDuration` 与
> `translateY` 位移、侧栏宽度/状态与其 `transitionProperty`、`--dur-base` 计算值。
> 位移或宽度出现小数即为动画中途（终值必为整数），可用来确认是否真的在插值 ——
> 这条读数曾直接抓出过一次 bug：某条"只过渡颜色"的规则把侧栏的 `width` 过渡覆盖掉了。
>
> 注意 CSS 里 **`width` 与颜色必须写在同一条 `transition` 声明中**，否则后写的规则会整条覆盖前者。

**默认窗口**：屏幕的 **75%**（宽高各 75%），在可用区域内**精确居中**（排除菜单栏 / Dock）。
不使用 `setFrameAutosaveName`，避免上次的位置尺寸覆盖默认值。

**首次打开**：没有任何本地数据时，会自动载入两份内置说明 —— **`README(EN).md`（纯英文）** 与
**`README(ZH).md`（纯中文，ZH 是中文的英文缩写）**，各自完整覆盖打开文件 / 阅读 / 编辑 / 快捷键 / 外观。
有测试保证英文那份里不含任何中文字符。

**命令行参数**（外壳，仅在需要时用）：
`--theme=<id>` 主题 · `--lang=zh|en` 界面语言 · `--fps=<n>` 帧率上限 · `--debug` 直接展开调试面板 ·
`--w/--h` 窗口尺寸（默认 75%）· `--br/--bl/--x/--y` 窗口位置 · `--wipe` 清空本地数据（等于第一次打开）·
`--settings` 直接展开设置面板。
> 踩过的坑：查询参数**必须拼在 `#` 之前**（`index.html?theme=x#debug`），否则会落进 fragment、全部失效；
> 另外用 `open` 启动的应用**不继承 shell 环境变量**，所以窗口几何当初用 env 传是无效的，现已改命令行参数。

### 沉浸式阅读（`F11` / `Ctrl+I`）
隐藏标题栏、侧栏、工具栏与状态栏，只留正文：阅读区自动加宽留白（8vh 顶 / 40vh 底），
鼠标移动唤出底部悬浮控制条（滚读进度、上下文件、字号加减、退出），2.2 秒无操作自动淡出。
`Esc`、`F11`、`Ctrl+I` 或点「退出沉浸」都能返回。

### 改了前端却看不到变化？—— 缓存
WKWebView 会缓存 `docviewer://` 的子资源，早期版本没发缓存头，导致**改了 CSS/JS 启动后仍是旧的**。
现在做了两件事：

1. `WKURLSchemeHandler` 的响应带上 `Cache-Control: no-store, no-cache, must-revalidate`，
   本地文件永远从磁盘读；
2. 启动时清一次 `WKWebsiteDataTypeDiskCache / MemoryCache / OfflineWebApplicationCache`，
   并用 `cachePolicy = .reloadIgnoringLocalAndRemoteCacheData` 加载首页。

另外前端资源链接带版本号（`?v=N`），改动 `index.html` 引用时可一并递增。
**排查建议**：F3 调试面板「性能」页顶部会显示 `文件行对齐`、`侧栏过渡` 等**浏览器实际计算值**，
一眼就能看出跑的是不是最新代码。

### F3 调试面板

| **文档** | 文件名 / 相对路径 / 类型 / 字节数 / 编码 / 行数 / 字符数 / 词块数、解析耗时、DOM 注入耗时、视图模式、字号与换行状态、解析告警 |
| **环境** | User-Agent、语言、平台、CPU 线程、窗口与屏幕尺寸、DPR、色深、`TextDecoder`/`localStorage`/`ResizeObserver`/`WebAssembly` 支持情况、GBK 解码能力、页面 URL 与协议、启动与就绪耗时 |

#### 关于帧率：为什么以前锁死 60

`requestAnimationFrame` **被浏览器锁在显示器刷新率上**（60Hz 屏就是 60fps），所以只往下限、不能往上走 ——
120/180/240 全是摆设。现在动画循环改用 **`setTimeout` 按 1000/cap 驱动**，实测：

| 上限 | 实测动画帧率 | 时间步进 | 画面帧率(显示器) |
|------|-------------|----------|-----------------|
| 30 | 31.0 fps | 33.33 ms | 58.2 fps |
| 60 | 59.9 fps | 16.67 ms | 59.9 fps |
| 120 | 122.1 fps | 8.33 ms | 59.1 fps |
| 180 | 180.1 fps | 5.56 ms | 61.4 fps |
| 240 | 240.4 fps | 4.17 ms | 61.6 fps |

> 60Hz 屏幕每秒仍然只显示约 60 张画面。高于刷新率的收益是**更细的时间步进**：
> 缓动、滚动、滑动的插值更密，观感更顺 —— 而不是"屏幕上更多帧"。

**CPU 实测**（应用进程 + 它新增的 3 个 WebKit 进程，`top` 瞬时值）：

| 帧率上限 | 应用进程 | WebKit | 合计 |
|---------|---------|--------|------|
| 60 fps | 2.8% | 5.9% | **7.9%** |
| 240 fps | 3.1% | 6.2% | **8.1%** |

帧率提高 4 倍只多 0.2% —— 因为每帧真正的工作被压到了最小。
（曾经每帧写 `textContent`，240fps 下就是每秒 240 次样式重算，已节流到 4Hz。）

#### 关于帧率：两个指标，别混为一谈

调试面板里是**两条独立的度量**，之前把它们混成一个数字，结果出现过「884694 FPS」这种
既没渲染任何画面、又把主线程占满的假指标。现在分开：

| 指标 | 来源 | 含义 |
|------|------|------|
| **渲染帧率** | `requestAnimationFrame` | 真正交付出画面的速率，受显示器刷新率与主线程负载限制。这才是"快不快"的答案 |
| **每秒调度次数** | 高帧率探针 | 主线程在**不渲染**时每秒能处理多少个任务。数值可以很高，但不代表流畅度 |

探针默认**开启但带 CPU 预算**（约 4 万次/秒，实际占用可忽略），想要真实上限可以勾上
「放开 CPU 预算」—— 那时它会跑满一个核心，测出来的是这台机器主线程的吞吐天花板。
不想要就取消勾选「高帧率探针」，开销归零。

所有真正吃 CPU 的部分仍然按频率节流：

| 工作 | 频率 |
|------|------|
| 帧计数 / 帧间隔统计 | 每渲染帧（仅几次算术） |
| 标题栏 FPS 徽标 | 每 500 ms 写一次文本 |
| 调试面板 KV + 曲线 | 最高 10 Hz / 20 Hz，且仅面板打开时 |

**帧率上限**在设置里可选 30 / 60 / 120 / 180 / 240 / 不限，由 `js/frames.js` 统一执行：
`requestAnimationFrame` 负责渲染帧，动画回调按设定的间隔分档触发，两者共用同一份帧计数。
所有动画（面板滑入、色块悬停、沉浸控制条、进度条、文档入场）都挂在这个调度器上，
所以改帧率是全局一致的，调试面板里能看到「动画帧率 vs 渲染帧率 vs 上限」三个读数。

曲线纵轴上限 75 fps（只是显示刻度），240 点采样窗口；旁边会显示采样到的显示器刷新率，
方便判断当前帧率是"跑满刷新率"还是"被负载拖住"。

## 实现要点

**RTF 多字节转义**
RTF 里中文常写成 `\'d5\'fd\'b3\'a3`，逐字节解码会产生 U+FFFD。解析器把连续的
`\'hh` 收集进字节缓冲，遇到非字节内容时整段交给注入的解码器（默认按 `\ansicpg`
选择 GB18030 / Big5 / CP1252）—— 这是中文 RTF 能正确显示的关键。

**文本 run 切分**
RTF 的样式是"状态 + 组栈"：`{\b 加粗}` 只在组内有效。解析器在每次样式签名变化
和每次出组时切分文本 run，按当时的样式生成 `<span>`，并复用同前缀的 span 缓存，
所以 `正常文本：` 与 `加粗` 能分别落在正确的 span 里。

**惰性列表项**
`\pntext` 是列表项的唯一权威信号：解析时只写入内部标记，真正建立 `<ul><li>` 放在
文本落盘时（`flush`），从而把 Word 常见的 `\pard{\pntext…}{\fi\li 文本}` 三段式结构
正确合并成一个列表项。

**拼接为什么不复制文本**
拼接条目持有原文件条目的引用（`parts`），渲染时按段拼出 HTML —— 不深拷贝、不写回、
不改动任何磁盘文件；「拆开」就是把同一批对象按原顺序放回列表。

**选中文件为什么不重建列表**
早期实现里 `select()` 会调 `refreshList()`，而它是 `innerHTML = ''` 整表重建 ——
于是每点一次文件，所有行的入场动画都会重播一遍，看起来像"闪一下刷新"。
现在分成两条路径：`refreshList()` 只在**结构真的变了**（增删文件 / 筛选 / 拖动排序 / 拼接）时重建；
选中、勾选只走 `syncRowClasses()` 就地改类名，DOM 节点保持不变，也就没有多余的动画。

**就地编辑怎么保证不改坏文件**
- **纯文本类**（txt / code / 源码视图）：直接编辑文本，保存时按**原文件编码**写回（GB18030 / Big5 / Shift-JIS / UTF-16 都支持，编不出来宁可报错也不写乱码）
- **RTF**：编辑的是渲染后的正文，保存时把它**反向序列化回 RTF** —— 文件开头的字体表 / 颜色表 / 样式表**原样保留**，正文重新生成时沿用文件自己的 `\fN` / `\fsN`，
  中文写成 `\uN?` 转义，所以与文件原本的编码无关、不会破坏原有字节；粗体/斜体/下划线等会往返保留
- **Markdown**：**不参与编辑**。渲染后的 HTML 转回 Markdown 会丢格式（表格、链接、代码块），
  与其做个有损的编辑，不如保持它原来的渲染显示完全不变
- 任何时候首次写入都会先留一份 `path.bak`；写失败时文件保持原样

**代码文件怎么处理**
源码与配置文件一律按**纯文本**视图渲染（`doc.textContent`，保留缩进与换行），不做语法高亮 ——
好处是不会因为转义或标记解析把 `<>`、`&`、模板字符串弄坏。类型名走 `DV.KIND`，
在状态栏 / 标题栏显示时经过 `DV.t()`，所以中英文都正确。

**i18n 怎么做**
以「中文原文」为 key 的词典（`js/i18n.js`）。静态界面由 `DV.applyI18n()` 遍历文本节点 /
`placeholder` / `title` 替换 —— 首次替换前把原文存在节点上，所以可以反复中英来回切；
JS 里拼出来的动态文案（状态栏的 `行 / 字符`、调试面板的指标名等）走 `DV.t()`。
有两条**静态覆盖测试**：`index.html` 里的全部文案 + `settings.js` 里所有列表项 label/note/desc，
缺译文就报错 —— 主题名、字体名这类由 JS 生成的文案也跑不掉。

> 注意：JS 生成的控件文案改了语言要**重画**（`SettingsUI.rebuildForLang()`），
> 只靠 DOM 扫描管不到；「恢复初始设置」也必须原地复位并重画，不能依赖 `location.reload()`，
> 否则会出现"主界面英文、侧栏中文"的混排。

**"文字看不清"的一个真实原因（RTF 颜色表）**
RTF 的颜色表第一项通常是空的，表示"自动色"（跟随阅读器）。解析器早期无条件把它当成黑色，
于是 `\cf0` 的正文被写成 `color:rgb(0,0,0)` —— 在深色主题下就是黑字黑底。
现在空项存 `null`（不输出颜色），正文自然跟随阅读器配色；若文件里确实指定了
与阅读背景对比度过低（<3:1）的颜色，还会自动回退为阅读器配色（可在设置里关掉）。

**RTF 字体为什么要能覆盖**
RTF 自带字体表与绝对字号（例如 TextEdit 导出的正文是 `\f0 Helvetica` + `\fs36` = 18pt），
这会让正文比阅读器设置大一圈、字号滑杆也失灵。开启「RTF 使用阅读器字体与字号」后，
用 `body[data-rtf-font="reader"]` 加一组 `!important` 覆盖解决 —— 属于呈现层覆盖，**不触碰原文件**。

注意选择器要写成 `.doc .rtf-body` 而**不能**是 `.doc.rtf .rtf-body`：**合并文档**的类名是
`.doc.merged`，里面同样嵌着各来源的 `.rtf-body`。写成后者会导致拼合后各段仍各用各的字号字体
（实测：18pt 与 10pt 的两个 RTF 合并后看起来还是两种大小）。现在合并在内的所有 RTF 内容
都会统一成阅读器排版，MD 分段也不例外。

**设置为什么只用 CSS 变量**
设置面板改的不是 DOM 结构，而是一批 CSS 自定义属性（`--doc-size` / `--doc-line` / `--doc-width`
/ `--doc-color` / `--accent` / `--font-custom`）加几个 `body[data-*]`（`data-theme` / `data-font`
/ `data-anim` / `.immersive`）。因此切主题不会重建文档、换字体不会触发重新解析，
改字号也不会让滚动位置丢失 —— 浏览器只做一次重排。

**为什么不用 MessageChannel 刷帧**
`postMessage` 只排一个宏任务、不留空档，浏览器会立刻兑现下一条消息 —— 于是"帧率"能在
一秒里涨到几十万，但一次画面都没渲染，纯粹是把主线程占满。因此渲染帧率只认
`requestAnimationFrame`；要测主线程吞吐就单独用探针，并给它明确的 CPU 预算。

**Markdown 列表建树**
列表先解析成 `{items, children}` 树再渲染，避免用字符串后处理闭合标签时产生非法嵌套。

**RTF 换行：`\par` 不存在的现实**
实测 28 个真实章节（TextEdit 导出）里 `\par` / `\line` 数量**全是 0**，换行只有两种形态：
每 ~255 字节一个 `\<换行>`（编辑器硬折行，按 RTF 规范属"可忽略转义符"），以及裸 `\n`。
而"空行=分段"的判断会被硬折行干扰（折行与分段连在一起，长得一模一样），
任何合并策略都会把作者的分段吞掉 —— 整篇挤成 4423 字的巨段。
现在的策略是**每个源文件换行都输出一个 `<br>`**（宁可多几个换行，也不能丢结构），
设置里保留「RTF 按源文件换行」开关可切回严格规范行为。
28 个文件的最长段从 33291 字降到 617 字。

**中文引号变成 U+0093 / U+0094（C1 控制符）**
macOS 文本编辑把智能引号写成 CP1252 的 `\'93` / `\'94`。这两个字节在 GBK 下不是合法组合，
会走"逐字节兜底"分支 —— 而 `String.fromCharCode(0x93)` 得到的是 C1 控制符 U+0093（不可见/乱码），
CP1252 里它应该是 `“`。现在 0x80–0x9F 区间统一按 CP1252 映射还原：
`0x93→“`、`0x94→”`、`0x91→‘`、`0x92→’`、`0x97→—`、`0x85→…`。
实测 21 个含引号的章节、1700+ 个引号全部正确。

> 已知歧义：两个 CP1252 字节**紧挨着**时（`\'93\'94` 相邻），按 GBK 也会解出一个合法字符（摂）。
> 解析器优先按文档声明的代码页（GBK）解释，这是更合理的选择；实际文件中引号总是被其它字节隔开。

**RTF 编码的三种坑（都踩过，已修）**
1. **多字节 `\'hh`**：`\'d5\'fd` 是 GBK 的"正"，必须把连续字节收集起来整段解码；逐字节必然得到 U+FFFD。
2. **孤立 CP1252 字节**：macOS 文本编辑器会把智能引号写成单个 `\'93` / `\'94`，
   它们不属于 GBK 双字节序列。这类字节若和邻近字节拼在一起解码就会变成替换符 ——
   现在遇到整段解码失败会退化为逐字节解码（`\'93` → `\u201C`），不再产生 U+FFFD。
3. **`\uN` 与 `\'hh` 混排**：`\u31532` 这类转义是字节序列的天然边界，
   解析到它时必须先把待处理的字节落盘，否则前后两段的字节会被错误拼接。

已用 28 个真实章节 RTF（macOS TextEdit 导出、cp936、含 5773 个 `\uN` 转义与 170 段 `\'hh`）
做全量回归：全部正常还原，无替换字符。

**编码回退链**
`TextDecoder(..., {fatal:true})` 逐级尝试：BOM → UTF-8 → GB18030 → Big5 → Windows-1252，
全部失败才用非致命 UTF-8 替换非法字节，保证任何文件都能打开而不是报错。

## 已知限制

- RTF 表格只做基础的行/列还原（不解析边框样式与合并单元格）
- RTF 不渲染 `\pict` 内嵌图片、页眉页脚、脚注、域（会被安全跳过）
- Markdown 不解析引用式链接定义与内嵌数学公式
- 单文件持久化上限 400 KB、会话总量 4 MB（超出仅保留在内存中并写入警告日志）
